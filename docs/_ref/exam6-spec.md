# Practice Exam 6 authoring spec (long-scenario simulation)

Exam 6 trains reading stamina as well as knowledge. The candidate (failed CCAR-F with 656, pass 720) found the real exam's scenarios long and started misreading them late in the exam. Every Exam 6 item has an exam-length stem with realistic detail, decoy constraints and one or two red herrings, so the decisive clue must be found by reading carefully.

Form: `exam6`, scenarios S2, S3, S5, S6, 60 items (15 per scenario), 120 minutes. Domains: D1 17, D2 11, D3 12, D4 11, D5 9. 8 multi-response items (select 2). Every one of the 30 task statements is touched.

Read with this file: `docs/_ref/question-spec.md` (base schema and distractor patterns), `docs/_ref/facts.md`, `docs/_ref/handbook-facts.md`, and the task statements in `docs/_ref/exam-guide.txt` (section 6, lines 113-718; sample questions lines 830-1050).

## 1. File format
- 8 part files in `js/data/exams/`: `exam6-S2a.js` (items 01-08), `exam6-S2b.js` (09-15), and the same for S3, S5, S6.
- Each file: a one-line comment, then exactly one `CCAR.addQuestions('exam6', [ ... ]);`.
- Use **backtick template literals** for every text field (stem, options, explanation, rationales, signals, trap). Inside them: never type a literal backtick (use `<code>` tags); write `${` as `\${`; apostrophes and double quotes need no escaping. Real newlines are fine; inside `<pre>` they are shown as line breaks, so start code lines flush left.
- HTML allowed: `<p>`, `<code>`, `<pre>`, `<b>`, `<i>`, `<br>`, `<ul>`/`<li>`. Inside `<pre>`/`<code>` write `<` as `&lt;`, `>` as `&gt;`, `&` as `&amp;`.
- Fields: `id` (`e6-S3-07`), `scenario`, `domain`, `obj`, `type` (`single`|`multi`), `select` (1 or 2), `stem`, `options` (4 for single, 5 for multi), `answer` (zero-based indices; use the index given in the plan), `explanation`, `rationales` (one per option, same order), `trap` (plain text, no HTML), `signals`.

## 2. Stem anatomy (the point of this exam)
Length: **130-230 words of prose** outside `<pre>` blocks (the validator rejects fewer than 120). About 40% of items also include a `<pre>` block of 5-18 lines (config, code, CLI invocation, trace or log excerpt, JSON). Use 2-4 `<p>` paragraphs:
1. Context: a fictional company and product, what is being built, the architecture (agents, tools, files, flags), scale numbers.
2. Evidence: what was observed (metrics, traces, logs, user reports, config). Put the decisive clue here, stated plainly but not highlighted, among other true details.
3. Constraints and noise: stakeholder requirements, budgets, policies, "cannot change X this quarter". Include 1-2 red herrings: details that are true and plausible but irrelevant to the root cause (a recent model upgrade, a latency figure, a lint change, the team's editor). Constraints must be the kind that eliminate specific distractors.
4. The ask, one sentence, as the last paragraph: "What is the most likely root cause?", "Which change is the most effective first step?", "Which design best satisfies all three requirements?", "What will happen when...?", "Which two changes...? (Select 2.)".

Rules: every stem uses a different company and product; realistic names and numbers; no real companies except well-known tools (GitHub, Jira, Sentry, Kafka, Postgres, Datadog, Slack); the stem must not contain words that appear only in the keyed option (no giveaways); the question must be answerable from the stem plus exam knowledge; exactly one best answer (or exactly two for multi).

## 3. Options
- Full sentences, **20-40 words each**, all options within about 30% of each other's length. The keyed option must not be the longest in more than 2 of your single-answer items. Describe a concrete mechanism in each option, often with a short "so that / because" clause.
- Every distractor is something a competent engineer might actually propose. Use the patterns in question-spec.md; each plan entry names the distractors to use.
- Never "all/none of the above", never refer to other options by letter (options are shuffled at runtime).
- Multi items: stem ends with "(Select 2.)"; both keys are independently correct; the three distractors are tempting.

## 4. Explanation, rationales, signals, trap
- `explanation` (**90-170 words**, at least 350 characters): state the principle, map the stem's evidence to it, show why the key satisfies every constraint, say why the most tempting distractor fails, and add an exam-guide versus current-docs note when relevant (for example "Task tool, named Agent in current SDK releases").
- `rationales` (20-60 words each): why this option is right or wrong in this scenario, citing stem details. The keyed ones start with "Correct."
- `signals` (35-80 words): "Decisive: ... Noise: ..." naming the detail(s) that settle the question and the red herring(s) to ignore. This is shown to the candidate as reading coaching.
- `trap`: short plain-text label of the distractor pattern.
- Style: US English, no em dashes anywhere (use commas, colons, semicolons, parentheses), no exclamation marks.

## 5. Accuracy rules
- Use only facts in facts.md, handbook-facts.md and exam-guide.txt. Never invent CLI flags, frontmatter fields, SDK options, API fields or behaviors. Deliberately fake features are allowed as distractors at most once per part file, and only ones listed as non-existent in facts.md (`--batch`, `--headless`, `CLAUDE_HEADLESS`, `--max-cost`, `--ci`, `.claude/config.json` commands array).
- Follow the exam guide framing where it differs from current docs, and mention the current name in the explanation: subagents are spawned with the **Task** tool (Agent in current releases); `/memory` verifies loaded memory files (`/context` also shows it).
- tool_choice items: state in the stem that the pipeline runs on **Claude Haiku 4.5** (which still accepts `any` and forced tool choice), so the exam answer is also correct in current docs. The explanation notes that Opus 5.5, Sonnet 5.5 and Fable 5.1 return HTTP 400 for `any`/forced and use strict tool use or structured outputs instead.
- Do not make a skill's `allowed-tools` semantics the deciding point (the guide and current docs differ).
- Model names: Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 4.5.
- Out of scope, do not test: streaming/SSE, rate limits, pricing calculations, prompt-caching internals, fine-tuning, embeddings/vector DBs, computer use, vision, auth/billing, cloud-provider config, tokenization. Batch SLA arithmetic is in scope (task 4.5).

## 7. Writing procedure (for each part file)
1. Read this spec, question-spec.md, facts.md, handbook-facts.md, and the task statements your items test.
2. `fs_write` the file with the header comment, `CCAR.addQuestions('exam6', [` and your first 2 items. Then `fs_append` 2 items at a time. Finish with `fs_append` of `]);`.
3. Run `node --check js/data/exams/<file>` and `node tools/validate.js --file js/data/exams/<file>`. Fix every ERR and re-run until it prints OK. Do not run the validator without `--file` (other parts are written in parallel) and do not edit any other file.
4. Reply with one line per item: id, obj, keyed idea, and any fact you were unsure of.
